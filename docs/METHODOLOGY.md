# 研究方法与证据分级

本仓库的结论只接受三类证据，按强度降序：

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| A（代码级） | 反编译代码中可被直接引用的判定逻辑、门禁条件、调用关系 | `if (崩溃标志 >= 3) { return; }` 早退分支 |
| B（字节级） | 线上抓取的真实报文字节，按协议规范逐字段解码并与代码预期一致 | 回执帧命令字、长度字段、msgId 三项同时吻合 |
| C（行为级） | 设备侧可观测的副作用（新连接、DNS/SNI、请求路径） | 注入消息后出现新的 443 连接 |
| —（不采用） | 运行日志、界面提示、第三方转述 | 应用自身打印的业务日志 |

日志不采用的原因：目标应用存在多渠道日志开关与远程日志上报，日志缺失不能推出逻辑未执行，日志存在也不能推出逻辑已执行。

## 1. 逆向流程

1. **定位包与组件**：从设备侧应用清单获取包名与版本，下载对应 APK；
2. **反编译**：使用 apktool 获取 smali 与 Manifest；
3. **调用链回溯**：以「网络入口」或「系统入口」为起点，向上追到触发源，向下追到最终副作用；
4. **门禁枚举**：对每个 `if` 分支记录判定表达式与默认值，给出「在何种设备状态下通过」；
5. **交叉验证**：同一事实至少由两处独立代码或一处代码 + 一处字节证实。

反编译树的检索必须使用脚本（`os.walk` + 容错读取），不能用 shell 通配符递归，否则会因路径过长而中断且无有效输出。

## 2. 协议验证流程

1. 依据代码中的常量与分支写出编码器；
2. **离线回读**：用自己的解码器把编好的帧解回结构体，比对字段；
3. 与线上真实帧逐字节对齐（长度字段、命令字最常见出错点）；
4. 现场发送，观察是否收到对端回执；
5. 回执中的关联标识必须与发送时的标识一致，方可判定「对端已解析」。

判定要点：回执只是「解析成功」的证据，不是「业务已执行」的证据。协议实现中回执通常早于业务分发，且回执发送失败会阻断分发。

## 3. 副作用归因流程

当需要判定「某条消息是否被业务层消费」时：

1. 先建立基线：静默观察一个足够长的窗口，记录设备的周期性行为（心跳、遥测、探测）；
2. 只改变一个变量（发送一条消息），其余环境不变；
3. 观察窗口覆盖该业务分支的最长延时路径；
4. 重复至少两次，排除偶发；
5. 若对照组与实验组无可区分差异，则判定「未观测到副作用」，而不是「已执行」。

周期行为（例如每分钟固定秒数的上报）是常见的误归因来源，必须先建立基线再下结论。

## 4. 现场环境要求

- 观测设备必须在同一广播域内，且具备链路层收发能力；
- 观测进程需要提权，否则只能看到广播/组播报文；
- 抓包过滤表达式应尽量宽（例如只按 `ip`），在应用层再做精确过滤；在部分驱动上，带端口条件的过滤表达式会完全失效；
- 应答器与被观测设备之间的字节序号必须由**同一进程**维护，否则自造数据会污染对端接收窗口，引发重传与连接重置。

## 5. 结论表述规范

- 「已确认」仅用于 A 级或 B 级证据；
- 「已观测」用于 C 级；
- 「假设」必须给出可证伪的判据与下一步探针；
- 任何依赖人工操作的步骤不计入自动化链路。
